## 一、结论摘要

> **TTFT 高是「账号级限速」，不是 IP、不是并发、不是协议、不是反代。**

## 三、是否降智 —— 否

### 3.1 vm-gpt-07 实测

| 项目 | 结果 |
|---|---|

### 3.2 判据

```
「降智」= 答案错误（历史上曾出现同一题答 29 而正确是 22）
「慢」  = 答案正确但延迟高 / 长题超时

vm-gpt-07 属于后者：不降智，单纯慢。
vm-gpt-06 / 09 当前额度耗尽，无法测试，但历史无错误答案记录。
```

## 四、换 IP 对照实验（2026-10-28 13:2x）

**方法**：同一槽位 `vm-gpt-07`，仅更换出口代理，其他条件不变。

| 阶段 | 出口代理 | 3 次耗时 | 平均 |
|---|---|---|---|
| 换绑前 | `198.145.102.173`（RCN 住宅，6 槽共用） | 8s / 9s / 3s | **6.7s** |
| 换绑后 | `px-local`（OVH 数据中心，独享） | 6s / 19s / 14s | **13.0s** |

**结果**：换到新 IP 后**更慢**（13.0s vs 6.7s）。实验后已还原。

**旁证**：
- 同一 IP 下 `vm-gpt-10` = 6.9s（快）
- 独享 IP 的 `vm-gpt-02` = 16.1s（慢）

**三个独立证据共同排除 IP 因素。**

## 五、并发与 TTFT 的关系（否定「降并发」方案）

按「同一分钟内该槽的并发请求数」分桶统计：

| 并发数 | 样本量 | 平均 TTFT |
|---|---|---|
| 1 | 160 | **29.0s** |
| 2 | 220 | 18.8s |
| 3–4 | 389 | 13.6s |
| **5+** | **2,875** | **9.6s** |

**并发越高，TTFT 越低**（高并发时段短请求占比大）。

**推论：把并发从 4 降到 2，TTFT 预期从 9.6s 升到 18.8s —— 反向恶化。**

## 七、根因

```
账号级限速（上游对该账号的调度优先级低）
```

**证据链**：
1. 同 IP、同协议、同模型，仅账号不同 → TTFT 差 4.8 倍
2. 换 IP → 无效（实测更慢）
3. 降并发 → 无效（负相关）
4. 协议/模型/服务层 → 完全一致
5. 反代开销 → 毫秒级，占比 < 3%

**与历史调查结论一致**（`sub2api-gpt-findings-2026-10-04`）：

> 「降智/慢速是账号在上游的信用状态，链路侧没有任何可改变它的自变量。」
