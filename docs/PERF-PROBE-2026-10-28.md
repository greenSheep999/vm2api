# vm2api Codex 槽位性能探测报告（完整版）

- **日期**：2026-10-28
- **环境**：OVH `40.160.37.212`，vm2api **v1.4.020**（自建镜像 `ghcr.io/greensheep999/vm2api`）
- **对照环境**：vps196 `s2a.muxpay.xyz`，sub2api（`ghcr.io/greensheep999/sub2api-codex`）
- **数据窗口**：2026-10-27 13:00 ~ 2026-10-28 07:30 UTC
- **样本量**：vm2api 3,934 条；sub2api 1,310 条（仅比较 135–138）

---

## 一、结论摘要

> **vm2api 平台本身没有性能问题。**
> TTFT 的差异 **95% 由「账号额度状态」和「上下文体积」决定**，与 IP、并发、协议、平台无关。
> 铁证：同一批 Plus 账号（137/138）在 **sub2api 上 6.4 秒，在 vm2api 上 2.9–3.3 秒** —— vm2api 更快。

**已排除的原因**：IP、代理、并发、排队、协议、UA、平台实现。
**确认的原因**：账号额度（5h/7d 使用率）、上下文体积（input tokens）、推理强度（reasoning_effort）、上游整体过载。

## 四、逐项排除

### 4.1 IP / 代理 —— 排除

```
换绑前（198.145.102.173 RCN住宅）：8s / 9s / 3s   平均 6.7s
换绑后（px-local OVH数据中心）：   6s / 19s / 14s 平均 13.0s

换到新 IP 后反而更慢。已还原。
```

**旁证**：同一 IP 下 vm-gpt-10 = 6.9s（快），vm-gpt-07 = 28.6s（慢）。

### 4.2 并发 / 排队 —— 排除

```
瞬时并发 1  → 首字节 4.7s
瞬时并发 2  → 首字节 3.5s
瞬时并发 3  → 首字节 1.2s        （并发升高，反而更快）

重试率：attempt=1 占 99.8%（3794/3803）
无 pool_queue_timeout / wait_timeout 记录
```

### 4.3 持续请求 —— 排除

```
各槽「前 1/3 vs 后 1/3」TTFT：
  vm-gpt-01: 8013 → 8353  (+4%)
  vm-gpt-03: 12365 → 11267 (-9%)
  vm-gpt-07: 43148 → 17858 (-59%)
→ 没有「越用越慢」的趋势
```

**反而「请求越密越快」**：

| 请求间隔 | 平均 TTFT |
|---|---|
| < 2s | 9.3s |
| 2–5s | 9.7s |
| 5–15s | 9.4s |
| 15–60s | 17.1s |
| > 60s | **28.8s** |

（缓存热 → 快；缓存冷 → 慢）

### 4.4 反向代理（Caddy）—— 排除

```
/health 直连 1.3–3.6ms  vs  经 Caddy 23–256ms  （Caddy 有 TLS 握手开销）
真实请求 TTFB：直连均值 9.05s  vs  经 Caddy 均值 8.26s  （无系统性差异）
```

**Caddy 开销占比 < 3%，不是 10 秒级延迟的来源。**

### 4.5 协议 / 请求构造 —— 排除

```
via:           全部 codex-kernel（一致）
protocol:      全部 openai.responses（一致）
service_tier:  全部 default（一致）
模型降级:      0 条（requested == upstream）
```

**唯一差异**：UA
```
vm2api:  codex_cli_rs/0.160.0 (linux x86_64)
sub2api: Codex Desktop/0.162.0 (Debian 13.0.0; aarch64)
```
**但**：同一 UA 下 vm2api 也能跑 3 秒（11/12 实测），说明 UA 影响「速度优先级」而非「必然慢」。

### 4.6 上线前历史对照（vm-04，10-21~10-26）

```
vm-04（qisi6688@gmail.com，已删除的槽）38 条记录：
  input 7      → TTFT 7.8s
  input 219K   → TTFT 12.4s
  input 200    → TTFT 39.9s   ← 小 input 但极慢（和现在 vm-gpt-07 同现象）
```

**说明「账号本身不稳定」的问题在 10-21 就存在，不是新版本引入。**

## 五、根因

### 5.1 主因：账号额度状态

```
账号 5h/7d 额度接近或达到上限
    ↓
上游不返回 429，而是「静默降速」
    ↓
TTFT 从 3-5s 变成 20-33s
    ↓
额度窗口刷新
    ↓
TTFT 立刻恢复 3-10s
```

**证据**：05-09 五个槽在额度刷新后全部从 20-33s 降到 3-10s。

### 5.2 次因：上下文体积

| input 范围 | 平均 TTFT（findings 2026-10-04） |
|---|---|
| < 400K | p50 ≈ 6s（平坦） |
| > 400K | p50 = 14.9s（2.5 倍） |

### 5.3 次因：推理强度

| reasoning_effort | 平均 TTFT |
|---|---|
| xhigh | 11.0s（95% 的请求） |
| max | 30.2s（最高 136s） |

### 5.4 外部因素：上游整体过载

```
2026-10-28 05:00 起，server_is_overloaded 持续出现（50 分钟内 23 次）
全部 error_code = server_is_overloaded，无一例配置错误
```

## 七、结论

| 问题 | 结论 | 证据 |
|---|---|---|
| vm2api 有性能 bug 吗 | ❌ **没有** | 同账号跨平台 3s vs 6.4s |
| 慢的原因 | ✅ **账号额度 + 上下文 + effort** | 额度刷新后全恢复 |
| IP 有影响吗 | ❌ 无 | 换 IP 实测更慢 |
| 并发/排队有影响吗 | ❌ 无 | 瞬时并发越高越快；重试率 0.2% |

| 协议有影响吗 | ❌ 无 | via/protocol/tier 全一致 |
| UA 有影响吗 | ⚠️ 影响「优先级」不影响「必然慢」 | 同 UA 也有 3 秒案例 |
| 503 频繁吗 | ✅ 上游过载 | 全为 `server_is_overloaded` |

## 11.2 根因（三重叠加）

### ① 拆渠道导致漂移能力丧失

```
拆前：new-api-self（Pro key）覆盖 01–10 全槽 → 01 失败可漂到 03/07/08
拆后：new-api-self 只剩 01/02/03/04 → 而 01/02/04 是重灾区（26–35% 失败）
     → Pro key 的请求全部撞在坏槽上，无处可漂
```

实测 key 配置（修复前）：

| key | allowed_vms |
|---|---|
| new-api-self | **01,02,03,04** ← 最烂的三个都在里面 |
| new-api-plus-self | 05–10 |
| new-api-GPT-Pro-Stable-Self | 01–10 |

**vm-gpt-11/12（零失败、2.2s）没有任何 key 引用。**

### ② 粘性会话 TTL = 24 小时，把流量钉死在单槽

```

```


**两个会话占了 2484 次请求，把 01 和 03 钉死。** 权重完全失效。

### ③ 503 不在重试列表里

```js
// 修复前 src/lib/pool/codex-slot-pool.mjs:389

  (status === 500 || status === 502 || status === 504) &&   // ← 没有 503

```

**上游 overloaded 主要以 503 返回（`server_is_overloaded`），而 503 不在列表** → 直接透传给客户端，24h 内 153 次 503 全部未重试。

## 11.6 调度控制的待优化项

当前调度（`routing.pool.strategy = balanced` + `weight`）有四个结构性局限：

### ① 权重只在「首次分配」时生效

```js
// seat-planner.mjs: rankSeatCandidates
priority 相同时，按 occupancy（open/cap）排序，weight 不参与
```

**新会话按权重/occupancy 选槽，老会话永远跟着原槽。** 权重不是流量比例控制器。

### ② 当前流量 100% 压在 11/12

```
vm-gpt-11  27（75%）
vm-gpt-12   9（25%）
其他 10 个槽  0
```

**原因**：权重 20 + 粘性清空。**风险**：11/12 额度会被快速吃光。

### ③ 自动调度只看 TTFT，不看流量与额度

```python
# /usr/local/bin/vm2api-auto-weight.py
if p50 < 8000ms: weight = 20
elif p50 < 20000ms: weight = 5
else: weight = 1
```

**会把「TTFT 好」的槽权重拉满 → 流量集中 → 该槽又被压垮**（正是 11/12 现在的处境）。

建议加入两个因子：
- **流量因子**：`requests/hour` 超阈值时降权
- **额度因子**：`used_7d > 60%` 降权、`> 80%` 降到 1

### ④ 无「快慢分组」能力

vm2api 只有 API key 层面的 `group_type`（openai/anthropic），**没有槽位分组**。要实现「快槽 key / 慢槽 key」，只能靠 `allowed_vms` 手动维护。

## 11.8 教训

```
① 改配置前先记录「改前基线」，否则无法定位拐点
② 相关性不等于因果（effort vs 503 就是典型误判）
③ 拆渠道要同步检查 key 的 allowed_vms 是否覆盖健康槽
④ 粘性 TTL 24 小时在生产环境太长，1 小时更合理
⑤ 上游 5xx 重试列表必须覆盖 503（overloaded 的主要形态）
⑥ 跨境链路先确认 BBR，cubic + 小缓冲是高延迟杀手
```
